# 第十二章 统一编辑模式

> 状态：**编码完成，待本机验收**（2026-09-13）。
> 范围：Linux 桌面端为主（Android 沿用同一套代码，但本轮不验）。
> 上游：第四章（交互）只覆盖了「圈地 + 打孔」两条窄路径；
> 本章把它们收进一个**统一的编辑模式**，并补齐点/线/面/门牌的完整编辑能力。

---

## 1. 需求

用户原话（要点）：

> 把用户编辑功能**全部实现在编辑模式中**。在编辑模式，用户可以标点、连线、
> 指定连线围成的区域，并可以为这些点、线、面命名。区域可以是多种类型，
> 包括**道路、小区、阻隔**三种类型。
> 在线上用户可以填充**门牌**，指定名称、描述、权重。
> 然后在渲染时如果需要显示门牌，会获取该线上的所有门牌，**按权重在线上分布**。

拆成可执行的五件事：

| # | 能力 | 本章落点 |
|---|------|----------|
| 1 | 编辑模式（唯一入口） | §4 工具条 + 状态机 |
| 2 | 标点 / 连线 / **用线围成区域** | §4.2–§4.3 |
| 3 | 点、线、面**命名** | §4.4 四个表单 |
| 4 | 区域类型：**道路 / 小区 / 建筑 / 阻隔** | §3 模型调整 |
| 5 | 线上**门牌**（名称/描述/权重）+ 按权重分布渲染 | §5 分布算法 |

## 2. 勘察：现有能力的天花板

| 现状 | 问题 |
|------|------|
| 「新增封闭区块」= **一笔画圈地**，提交时一次性建 点+线+面 | 用户**不能先标点再连线**；线段本身不是一等公民 |
| 线只有 `kind`（边界/路），**没有名字** | 「为线命名」无从谈起 |
| 点**没有名字** | 「为点命名」无从谈起 |
| 区块的 `boundary_type` 是**墙/铁栏/河道** | 这是**材质**，跟用户要的「道路/小区/阻隔」不是一回事 |
| 线靠 `lines.area_id` 挂到区块 | 一条线只能属于一个区块；两个小区共用一堵墙要画两遍 |
| `entities` 表 | **本来就为线上实体设计**：`line_id` / `line_index` / `line_weight`（注释写着"占线段的宽度"）/ `side_offset_m` —— 门牌直接落这里，不用新表 |
| 编辑入口散落 | 主按钮在「圈地 / 打孔」之间切换，删除只能通过长按/详情弹窗 |

**结论**：`entities` 表不需要动；`points`/`lines`/`areas` 需要动。

## 3. 模型调整（schema v4）

### 3.1 两条属性归属的纠正（用户拍板）

> **道路 / 小区 / 阻隔是一个区块的属性；
> 墙 / 铁栏 / 绿化带 / 河道 / 施工 / 软边界是一条线的属性。**

这条纠正非常关键，因为它解释了现实：

- 「大运城邦」是**小区**（区块的属性）；
- 它北面是**围墙**、东面是**河道**（每条线各自的属性）。

所以：

| 变更 | 说明 |
|------|------|
| `areas` 新增 `area_type`（`road`/`community`/`building`/`barrier`） | 区块的语义类型 |
| `areas` **删除** `boundary_type` / `boundary_height` | 材质不该挂在面上 |
| `lines` 新增 `boundary_type` | 材质搬到线上 |
| `lines` 新增 `name` | 线要能命名 |

### 3.1b 区域类型：四个取值（2026-09-13 追加「建筑」）

`areas.area_type` 现有四类：

| 取值 | 名称 | 说明 |
|------|------|------|
| `road` | 道路 | 能走的地方，寻路时要走进去 |
| `community` | 小区 | 有门、有门禁，只能从门进出（本 App 的核心场景） |
| `building` | **建筑** | 具体的楼栋本体，实心不可穿越 |
| `barrier` | 阻隔 | 纯障碍（河道、工地、山体），谁都不能穿 |

**建筑与阻隔的区别**：建筑**有确切轮廓**（你知道那栋楼长什么样），
而阻隔往往是一片说不清边界的障碍。地图上两者颜色也刻意拉开
（建筑蓝灰 vs 阻隔红）。

**加这一类不需要 schema 迁移**：`area_type` 是自由文本列、没有 CHECK 约束，
且所有读写都走 `AreaType.values` / `fromStorage`（未知值兜底为 `community`）。
备份文件同理 —— 老文件里不会出现 `building`，但读到它也能正确解析。

### 3.2 一条线可以同属多个区块（用户拍板）

新增关联表：

```sql
CREATE TABLE area_lines (
  area_id INTEGER NOT NULL REFERENCES areas(id),
  line_id INTEGER NOT NULL REFERENCES lines(id),
  sort_order INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (area_id, line_id)
);
```

`lines.area_id` **删除**。理由：两个相邻小区共用一堵墙时，那是**同一条线**。
存两遍的代价是——改一边另一边不跟着变，而且门/材质会分叉。
现在改一次两边都对。

代价：`assembleAreaRing` 从「按 `lines.area_id` 过滤」改成「按 `area.lineIds` 取线」；
导出格式要带上成员关系（见 §6）。

### 3.3 `LineKind` 保留但语义收窄

`kind` 与 `boundary_type` **正交**，都保留：

- `kind` 回答「**能不能走**」：`route_edge`（可通行）/ `area_boundary`（不可穿越）；
- `boundary_type` 回答「**是什么**」：墙 / 铁栏 / 河道 …

一堵墙既"不可穿越"又"是砖墙"；一条软边界既"可通行"又"是软边界"。
界面上就是一个二选一的分段控件 + 一排材质 chip。

### 3.4 迁移与数据安全

`userV4Statements`（`lib/core/schema.dart`）的执行顺序**不能调换**：

1. `points` 加 `name`；
2. 建 `area_lines`；
3. **趁 `lines.area_id` 还在**，把它灌进 `area_lines`；
4. 重建 `lines`：加 `name`/`boundary_type`（从 areas 带过来），去掉 `area_id`；
5. 重建 `areas`：`boundary_type` → `area_type`。

两个细节：

- **用「新建 → 拷数据 → DROP 旧 → RENAME」而不是 `ALTER TABLE ... DROP COLUMN`**：
  后者要求 SQLite ≥ 3.35 且对引用关系敏感；重建法是全版本通用的做法。
  整个迁移包在 sqflite 的 `onUpgrade` 事务里，失败整体回滚。
- **材质只回填给边界线**（`kind='area_boundary'`）：万一有内部路也被标了
  `area_id`，给它安一个"铁栏"材质是错的 —— 一条可骑行的路怎么会是铁栏？
  那种情况留 NULL（未指定材质）。

**类型推断**（老数据 → `area_type`）：`river`/`construction` → `barrier`，其余 → `community`。

**升级前自动备份**：`AppRepository.open` 在打开库之前，若文件已存在且
`user_version < 4`，先把整个 `.db` 复制一份成 `map.db.pre_v4.bak`（只做一次）。
v4 会 DROP + 重建两张表 —— 事务能保证失败回滚，但"回滚了但代码有 bug"和
"真把表搞坏了"在用户眼里没区别，而这是没有第二份的数据。

> **已用真实 SQLite 验证**（不是测试文件，是一次性脚本）：
> 造一个含 2 个区块 / 6 条线 / 1 个门 / 1 个门牌的 v3 库跑迁移 ——
> 行数一条不少、材质正确搬到线上、`area_lines` 建出 5 条关联、
> `route_edge` 没有被误安材质；全新 v4 建库的列结构与默认值也逐列核对过。

## 4. 编辑模式（UI）

### 4.1 入口

地图页右下角主按钮从「新增封闭区块 / 打孔」改成单一开关：
**「编辑我的地图」⇄「完成编辑」**。进入后顶部出现工具栏。

### 4.1b 首页外壳：去掉 TabBar（用户 2026-09-13 要求）

原来首页是三个 Tab：**地图 / 区块 / 设置**。现在改成：

```
Scaffold
  └─ body: MapPage(topTrailing: 设置按钮)
       ↑ 点按钮 → Navigator.push(SettingsPage())   ← 独立页面，带 AppBar 返回
```

两条理由：

- **「区块」Tab 从建库起就是占位页**，而区块的浏览/创建/改名/删除早已全部落进
  地图页的编辑模式。留着一个点进去是空的 Tab，比没有更糟 ——
  它会让人以为"还有个没做完的功能"。
- **地图是这个 App 唯一的主界面**。底部导航白占 56px，还让"我在哪一层"变模糊
  （切到设置页时地图仍在后台跑定位与查询）。设置不是"另一个主界面"，
  而是偶尔进去改一次配置的地方 —— push 一个页面进去、改完、返回，语义干净。

设置按钮做成 MapPage 的 `topTrailing` **插槽**而不是首页自己 `Positioned` 一层：
顶部状态条的文字长度是变的（缩放 / 要素计数 / 导入层摘要），浮动叠加迟早盖住它。
放进同一行后，两者永远不打架。`_StatusCard` 的左右外边距也一并去掉，
统一由外层 Row 给 8px，免得两边错开一截。

### 4.2 工具

| 工具 | 交互 | 产出 |
|------|------|------|
| **选择** | 点按要素（优先级：门牌 → 门 → 点 → 线 → 面） | 底部面板：改属性 / 删除 / 前移后移；**长按顶点可拖动** |
| **标点** | 点地图 | 落一个点 + 命名表单 |
| **连线** | 点两个点（附近有点则吸附，没有就地建点） | 一条线 + 属性表单 |
| **围合区域** | 依次点若干条首尾相接的线 → 闭合 → 命名 + 选类型 | 一个区块（**不新建任何点线**，只认领已有的） |
| **门牌** | 点一条线 | 门牌表单 |
| **门** | 点一条已属于某区块的线 | 门属性表单（复用 04 章的 sheet） |
| **一笔画圈地** | 连续点拐角 → 闭合 | 区块（**自带建点建线**，原「圈地」的快捷路径） |
| **选取底图** | 点底图上的路 / POI | 「是否带入为我的数据」→ 复制进用户层 |

**连线**与**围合**的分工就是用户那句话的字面意思：
先「标点、连线」，再「指定连线围成的区域」。
而**一笔画圈地**保留为快捷路径 —— 有时你就是想直接圈一圈，不想一条条连。

### 4.3 围合的校验

每点一条线都要满足「与已选线**首尾相接**」，否则提示
「这条线跟已选的线没有连在一起」。提交时再用 `assembleAreaRing` 校验一次能否
组成闭合环 —— **组不成环就不落库**，否则会存下一个永远画不出来的"空壳区块"。

每个端点恰好连 2 条线是闭合环的充要条件，这条实时校验让用户在点第二条线时
就知道自己选错了。

### 4.3b 两条交互红线（用户 2026-09-13 明确要求）

**（一）默认不与底图数据交互。**

底图是 OSM 的只读参考数据。以前**浏览态**随手点一下就弹
「要不要把这条路变成你的路网？」，问题有三：

1. 打断操作 —— 用户点地图绝大多数时候是想选自己的东西；
2. 容易误带入 —— 一旦带入就是独立数据，用户事后分不清哪些是自己画的；
3. 心智负担 —— 用户得时刻记得"别点到路上去"。

现在底图交互被收进**「选取底图」子模式**：只有进入编辑模式并显式选择该工具后，
点按才会命中 OSM 路 / POI。浏览态点地图只选自己的要素。
底图图层被隐藏时该工具会直接提示「先用左下角图层开关打开」，
而不是让用户对着空地图点半天没反应。

**（二）连线只吸附已有点，绝不新建点。**

连线的每一次点按 = **吸附到最近的已有点**；附近没有点就提示
「请先用『标点』工具落点」，而不是就地造一个。

为什么不做「附近没点就地建一个」（上一版的做法）：用户想连 A、B 两点，
手抖偏了几米就会凭空多出两个孤零零的顶点 —— 图上看着像连线"画歪了"，
实际是多了两条数据。**点的创建只走「标点」一条路**，
数据里有多少点、分别在哪，用户心里始终有数。

配套的两个细节：

- **吸附容差改成按像素算**（见 §4.3c）—— 否则"吸附"在手感上根本不成立；
- **要素 Marker 在非「选择」工具下让开点击**（`onTap: null`）。
  不然用户想点一个点当端点，手指正好落在那个点的小圆点上时，
  Marker 自己的 `onTap` 会吃掉事件，变成"选中了这个点"，连线永远连不起来。
  另外「连线」工具下把所有点画大一圈（白底 + 绿边 16px），
  明确告诉用户"这些就是能吸的靶子"。

### 4.3c 吸附容差按「手指大小」算

原实现给的是固定米数（zoom 15 时 24 m），换算成像素只有 **5–7 px** ——
手指根本点不中，用户会以为「吸附坏了」。现在按像素换算：

```
容差(米) = 每像素米数(zoom, lat) × 40px     // 40px ≈ Material 最小可点区域
```

| zoom | m/px | 容差 |
|------|------|------|
| 12 | 35.3 | 300 m（触上限） |
| 15 | 4.41 | 176 m |
| 17 | 1.10 | 44 m |
| 19 | 0.275 | 11 m |

这样无论缩放多少，屏幕上「能点中的范围」始终是同一个圈。

### 4.3d 点选歧义：区域 / 线 / 点到底选哪个（用户 2026-09-13 反馈）

**症状**：想点「道路区域」，结果总是选中它的边线。

**根因**：命中优先级是 `点 → 线 → 面`，且三者用**同一个容差**。
而区域的边线就是它的边界 —— 站在区域里，离边界永远不远。
zoom 15 时容差 176 m，一个 100 m 见方的区域站在正中离边界 50 m，
线依然"命中" → 区域**永远选不中**。区域越大越明显。

**修法**（用户建议的思路，落实为两级半径 + 连点切换）：

1. **精确半径**：点/线/门/门牌只有在 `0.35 × 容差`（≈10 px）之内才算"指着它"。
   手指半径（28 px）是为了**找得到**细小要素，不是为了**判得准**，两者不该混用。
2. **排序把区域夹在中间**：

   | 优先级 | 类别 | 条件 |
   |--------|------|------|
   | 1 | 门牌 / 门 / 点 / 线 | **精确命中**（≤ 0.35 × 容差） |
   | 2 | **区域** | 点在区域内 |
   | 3 | 门牌 / 门 / 点 / 线 | 只是宽松命中（≤ 容差） |

3. **同一位置再点一次循环切换**。几何只能猜"最可能"，猜错了得让用户能纠正。
   连点阈值取容差的 1/4（≈7 px），容得下手抖又不会把两次不同意图误判成连点；
   切换时会 toast 出"已切到「XX」"。

**同时把吸附容差从 40 px 收到 28 px**：40 px 在 zoom 15 下算出 70 m 的精确半径，
比 100 m 区域的半宽（50 m）还大 —— 光靠两级半径救不回来，必须一起调。

实测表（100 m 见方区域，站在正中离边界 50 m）：

| zoom | 容差 | 精确半径 | 结果 |
|------|------|----------|------|
| 15 | 123 m | 43 m | 区域赢 ✅ |
| 16 | 62 m | 22 m | 区域赢 ✅ |
| 17 | 31 m | 11 m | 区域赢 ✅ |
| 18 | 15 m | 5.4 m | 区域赢 ✅ |
| 19 | 7.7 m | 2.7 m | 区域赢 ✅ |

手指精确压在边线上 / 顶点上时，仍然是线 / 点赢（精确命中优先）——
这是刻意的：**精度换优先级**。

窄区域（比如 10 m 宽的道路）在低缩放下中心离边线只有几米，
线会赢；但区域仍在候选列表里，**原地再点一次就能选到**。

### 4.4 四个表单

| 表单 | 字段 |
|------|------|
| 点 | 名称 |
| 线 | 名称、**能不能走**（二选一）、边界材质（6+未指定）、通行代价、单向、备注 |
| 区域 | 名称、**类型（道路/小区/建筑/阻隔，带一句话说明）**、是否生效 |
| 门牌 | 名称、描述、**权重（滑杆 + 实时换算成"占这条线约 X%"）**、垂直偏移 |

门牌表单的权重滑杆旁边会实时算一句
「若其余 N 个门牌权重都是 1，它会占这条线约 X%」——
权重是个抽象数字，直接告诉用户结果比让他自己算有用。

### 4.5 草稿渲染

编辑态画到一半的东西（连线的起点、已选的线、圈地的拐角）由
`edit_overlay.dart` 单独渲染：橙色高亮已选线、绿色描边圈地多边形、顶点手柄。
和已落库的要素在视觉上分得很开 —— 用户永远知道"哪些已经存下来了"。

## 5. 门牌：按权重沿线分布

### 5.1 算法

> `entities.line_weight` 在 03 章的定义就是「线上实体的权重（即占线段的宽度）」。

所以门的读法是：**按权重把线切开，每个门牌落在自己那一段的中点**。

```
权重 w₁…wₙ，W = Σwᵢ
第 i 个：startT = (Σ_{j<i} wⱼ) / W
        endT   = (Σ_{j≤i} wⱼ) / W
        t      = (startT + endT) / 2      ← 落在自己那一段的中点
位置 = 线上 t 处，再按 side_offset_m 做垂直偏移
```

现实对应：一条街上店面占地宽度不同，门牌之间的实际距离自然也不同。

**顺序**由 `line_index` 决定（编辑模式可上下移动）——
排序必须稳定，所以 `line_index` 为 null 的老数据用 id 兜底，
保证「同一份数据每次渲染结果一致」。

**边界情况**（都有验证）：权重 null/≤0 一律按 1 算（不除零、不吞门牌）；
空列表返回空；单个门牌落在正中；两点重合时坐标退化但 `t` 仍按权重算。

### 5.2 渲染

门牌画成线上带边框的小胶囊（名字 + ×权重）。**显示权重是有意的**：
用户调完权重后能在线上直接看出「谁变得更宽了」，不用点开面板对数字。

左下角有「门牌」开关。为什么不永远显示：一条商业街几十个门牌时，
整屏小胶囊会盖住底图与区块边界。

## 6. 备份格式跟着升到 v3

第 11 章的备份格式必须跟上模型：

| 表 | 变更 |
|----|------|
| `points` | + `name` |
| `lines` | − `area_id`、+ `name`、+ `boundary_type` |
| `areas` | − `boundary_type`、+ `area_type`、+ **`line_ids`（成员关系）** |

成员关系放在 **area 侧**：一条线出现在多个区块的 `line_ids` 里，
备份里那条线**只存一份** —— 这正是「一线多区」的表达。

**导入语义的两处连带调整**（`core/merge.dart`）：

1. **线段键不再含区块键**：`"kind|点A|点B"`。
   一条线可以同属多个区块，键里塞一个区块就错了。
   归属关系由新的 `LinkAreaLines` op 单独表达（排在 line 之后执行）。
2. **门牌的实体键**从「名字 + 锚点坐标」改成 **「名字 + 所属线键」**：
   门牌挂在线上、没有 `point_id`，用老键会让**不同线上的同名门牌被误判成同一个**。

**向后兼容**：v1 / v2 备份照常可读 ——
老的 `lines.area_id` 在导入时被翻译成 `area_lines`；
老的 `areas.boundary_type` 按同一套规则推断 `area_type`。

### 7.1 控制器的「请求」模式

控制器里**没有** `BuildContext`，弹不了表单。所以状态迁移与 UI 之间用一层
挂起请求解耦：

```
用户点地图 → controller.onMapTap(p, data)
           → 按当前工具积攒几何（连线起点 / 已选线 / 圈地顶点）
           → 需要填表时把 EditRequest 挂到 state 上
页面 ref.listen → 收到请求 → 弹对应表单 → 把结果交回 controller.resolve*
```

好处是**每一个工具的行为都被限制在「积攒几何 → 发一个请求 → 收到结果落库」三步**，
不需要在 widget 里散布 `if (正在连线 && 点了第二个点 && ...)`。

### 9.1 手工验收步骤

cp ~/.local/share/com.example.map/map.db ~/map.db.pre_v4.manual.bak

再看一眼自动备份是否生成：
```bash

sqlite3 ~/.local/share/com.example.map/map.db \
  "pragma user_version; .tables; select count(*) from area_lines;"
```
期望：`4` / `area_lines areas entities gates lines points schema_meta` / 关联数 ≥ 0

**B. 默认不碰底图（用户 2026-09-13 的新要求）**

1. **不要**进编辑模式，直接点地图上的一条底图道路或 POI →
   应该**什么都不弹**（以前会弹「建立我的路网」）；
2. 点自己画的区块/线/点 → 正常选中并出面板；
3. 进编辑模式 → 选 **「选取底图」** 工具 → 再点同一条底图路 → 这时才弹带入对话框；
4. 把这个工具切走（比如切到「标点」）→ 再点底图路 → 又不弹了。

**C. 连线不造点**

1. 先只画 **2 个点**（标点工具）；
2. 切到「连线」→ 点第 1 个点附近（离 10 米以内）→ 底部提示变成「再点另一个已有点即可连线」，
   且被选中的点上有绿色"起点"手柄；
3. 点第 2 个点 → 弹出线属性表单（说明吸附成功）；
4. **关键**：切到「选择」工具数一下点的总数 —— 应该还是 **2 个**（没有凭空多出来）；
5. 再切回「连线」，点在一片**远离所有点**的空地上 →
   应该提示「附近没有已有点（吸附范围约 N 米）」，**而不是**造一个新点。

**D. 编辑模式走一遍**

1. 点右下 **「编辑我的地图」** → 顶部出现工具栏；
2. **标点**：点 4 个角 → 每个点都能命名；
3. **连线**：依次点两两相邻的点 → 连成 4 条边 → 给线填名字与材质（比如「实体墙」）；
4. **围合区域**：依次点这 4 条线 → 底部按钮变成「围合成区域（已选 4 条）」→
   点它 → 命名 + 选类型**「小区」** → 地图上出现紫色蒙层；
5. **门牌**：切到「门牌」工具 → 点一条边 → 填 3 个门牌，权重分别 **2 / 1 / 1** →
   确认它们**不是等距**的，第一个占的段明显更宽；
6. 点左下「门牌」开关 → 门牌整体消失/出现；
7. **选择**工具 → 点一个门牌 → 面板显示「占线长 50%」→ 点「前移」→ 位置变化；
8. **长按拖动**一个顶点 → 区块形状跟着变；
9. 点「完成编辑」。

再做一次 D 的 2–4 步，用**同样的 4 条边**围出第二个区域（比如叫「小区乙」）→
点第一条边时，面板应该显示「属于 小区甲、小区乙」。
删掉「小区乙」→ **「小区甲」的墙必须还在**（这是 v4 关联表存在的意义）。
