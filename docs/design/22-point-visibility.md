# 第二十二章 点的显示：浏览态不显示、编辑态按密度抽稀

> 状态：**编码完成，待本机验收**（2026-09-14）。
> schema **v11**（`points.processed` + `source` 多一个值 `recorded`）、备份格式 **v9**。
> 这一章不改任何几何，只回答一个问题：**哪些点该出现在地图上**。

---

## 1. 需求（用户原话）

> 当前点在地图上的显示影响视觉体验：
> 1. **非编辑状态不要显示点**，除非是**用户定位录入的但未处理**的定位点。
> 2. 编辑状态点的显示**过于稠密**了，如果地图**比例尺大到一定程度就不显示点**，
>    即便没有那么大，当点的显示**过于稠密时也只显示部分点**。

---

## 2. 实测：稠密到什么程度（真库 686 个点）

| 事实 | 数字 |
|------|------|
| 点数 | **686**（被线用到 542、孤立 144、有名字 12） |
| **最近邻 0.5 m 以内** | **273 个（40%）** —— 大量近乎重合的点（画线时同一处点了多次） |
| 最近邻距离 | 中位 7 m、90% 在 37 m 内 |
| 一屏（1200×800）内点数 | zoom 15 → **452**；16 → 228；17 → 56；18 → 6 |
| 来源 | 全是 `manual`，`gps` 0 个（Linux 无定位；「记录」在 Linux 上是手点地图） |

结论：不是错觉。zoom 15 一屏 452 个点、其中 40% 和邻居重合 —— 屏幕上是点墙，
既看不清路，也点不中任何东西。

---

## 3. 两个决策（2026-09-14 用户拍板）

| # | 决策 | 结论 |
|---|------|------|
| D1 | "未处理"怎么定 | **由用户自己标记**；已处理的**默认不显示**；**默认处于未处理状态** |
| D2 | 编辑态抽稀规则 | **屏幕 24 px 网格**，每格最多画 1 个 |
| D3 | 缩放阈值 | **zoom < 15 不显示**（编辑态的批量点） |
| D4 | 谁永远不抽掉 | **选中的点 + 折线草稿顶点**（有名字的点**不**豁免） |

### 3.1 D1 落地时冒出来的一个问题：什么叫"定位录入的"

用户要区分"**定位录入的**点"（浏览态要显示）与其它点。但库里分不出来 ——
「记录模式手点地图」和「编辑模式标点」存进去**都是 `manual`**：

```
记录模式 点地图落点   → source = manual   ←  其实是"我在这儿"的记录点
编辑模式 标点工具     → source = manual   ←  是画线用的顶点
```

而 Linux 上根本没有 GPS（`gps` 点为 0），也就是说**在 Linux 上"定位录入"只能靠手点**。
所以 v11 给来源补了一个值：

| source | 谁产生 | 浏览态显示？ |
|--------|--------|--------------|
| `manual` | 编辑模式「标点」 | ❌ 不显示（它是画图顶点） |
| **`recorded`** | **记录模式点地图** | ✅ 未处理时显示 |
| `gps` | 记录模式「记录当前位置」 | ✅ 未处理时显示 |

**老数据不追溯**：v11 之前"记录模式手点"的点存的就是 `manual`，无法分辨 ——
迁移把它们留在 `manual`。这恰好是它们绝大多数的情况（686 个里绝大多数是画线顶点），
而且结果是**浏览态一个点都不显示**，正是用户要的效果。

## 4. 规则（`core/point_density.dart`，纯 Dart）

### 4.1 浏览态：只显示"记录录入且未处理"的点

```dart
bool visibleInBrowseMode(PointRow p) =>
    p.deletedAt == null && p.source.isRecorded && !p.processed;
```

- 画图顶点（`manual`）→ 一个都不显示；
- 记录点但已标记"已处理" → 不显示（用户原话："标记已处理的定位点，默认不显示"）。

**实测**：真库 686 个点全是 `manual` → **浏览态显示 0 个**。

### 4.2 编辑态：缩放阈值 + 像素网格抽稀

| 规则 | 值 | 理由 |
|------|----|------|
| 缩放阈值 | **zoom < 15 一个点都不画** | 实测 zoom 12–14 一屏 661~686 个点（那几级上点连成一片）；地图 `minZoom` 是 12，这个阈值恰好把"看全省/看全镇"排除在外 |
| 抽稀网格 | **24 px**，每格最多 1 个 | 命中/吸附的手指半径是 28 px（`kFingerRadiusPx`）。24 略小于它：画出来的点屏幕上能分辨，没画出来的就在某个画出来的点旁边一两像素内 |
| 格内优先级 | **有名字的优先** → 其次 **id 小的** | 标签比匿名圆点信息量大；id 排序保证**决定论**（同一份数据每帧结果相同，不会闪） |
| 永远保留 | **选中的点 + 折线草稿顶点** | 正在编辑的东西不能在眼皮底下消失（用户明确只要这两个） |

**格子锚在地理坐标上**（把 24 px 换算成"这个缩放下的经纬度格子"），
而不是锚在屏幕上 —— 这样**拖动地图时点不会忽隐忽现**（同一个点要么一直画、
要么一直不画）。附带好处：纯算术，能用真实坐标在脚本里验证。

### 4.3 一个额外的例外：正在记录的点

`zoom < 15` 时**记录模式**仍然显示"未处理且已记录"的点 ——
不然你刚点下去的那个点会立刻消失（"我在记录，却看不见我记了什么"）。
这不是用户提的，是那条规则必然要补的一个口子。

## 5. 实测：抽稀后到底剩几个（真库 686 个点）

| 缩放 | 全库画出 | 一屏（1200×800，以点云质心为中心） |
|------|----------|-------------------------------------|
| zoom 15 | 188 / 686（27.4%） | **452 → 130** |
| zoom 16 | 284 / 686（41.4%） | **228 → 94** |
| zoom 17 | 383 / 686（55.8%） | **56 → 32** |
| zoom 18 | 496 / 686（72.3%） | 6 → 6（已经够疏，网格不再起作用） |
| zoom < 15 | **0**（只剩手上正在用的那几个） | 0 |

## 6. 数据模型（schema v11 / 备份 v9）

```sql
ALTER TABLE points ADD COLUMN processed INTEGER NOT NULL DEFAULT 0;
```

- **默认 0 = 未处理**，正是用户说的"默认处于未处理状态"；
- 老点自动成为"未处理"，而它们绝大多数是 `manual` → 浏览态本来就不显示它们
  → **这一版对现有地图的外观零影响**（实测：迁移后 0 个点被误标成已处理）；
- `source` 多一个值 `recorded`（自由文本列，**加值不需要迁移**）；
- ⚠️ `ALTER TABLE ADD COLUMN` **不幂等** —— 迁移分支必须挂在 `oldV < 11` 上（v10 同样）。

**标记入口**：点面板上的「标记已处理 / 改回未处理」（**只对记录录入的点出现** ——
给画图顶点一个"已处理"开关只会让人以为点错了按钮）。点面板副标题也会写
`记录录入 · 未处理`。

**备份 v9**：点多了 `processed: true/false`（写布尔而不是 0/1，肉眼看备份更直白）；
老文件没有这个字段 → 读成"未处理"。

cd ~/Projects/flutter/map

**A. 浏览态：一个点都不显示**

1. 不进编辑模式（没点「编辑」按钮）看地图 →
   **原来那一片点应当全部消失**，只剩区域、线、门、店铺标签、换路口旗标；
2. 放大到 zoom 18/19 也**不应该**冒出点来（浏览态与缩放无关，只是不显示）。

**B. 编辑态：抽稀**

1. 点「编辑」→ 点应当出现，但**明显比过去少**（同一个小格子里只留一个）；
2. 缩到 zoom 14 或更小 → **点全部消失**（说明"比例尺大到一定程度就不显示"生效）；
3. 回到 zoom 15 → 点回来；继续放大到 17、18 → 点**越来越多**（越放大越细）；
4. 拖动地图 → 点**不应该忽隐忽现**（格子锚在地理坐标上）；
5. 用「路线」工具拉线时 → **选中的点和草稿顶点始终可见**（即使它在密集区）；
6. 挑一个**有名字**的点（地图上有名字标签的）→ 它应当比周围匿名点更"容易被留下"。

**C. 记录模式：新记的点看得见**

1. 点「记录」→ 进记录模式 → 缩到 zoom 14（点本该不显示）→ 点地图落一个点 →
   **这个新点应当立刻可见**（正在采的东西不能藏），并弹出表单；
2. 保存后它仍在（未处理）；点「完成记录」退出 → 回浏览态 → 它**仍然显示**
   （记录录入且未处理）；
3. 点中它 → 面板应显示 `辅助点 · 记录录入 · 未处理`，
   并且有一个「**标记已处理**」按钮；
4. 点「标记已处理」→ 提示"已标记为「已处理」—— 浏览地图时不再显示这个点"，
   而它**当场地图上消失**；
5. 进编辑模式 → 它又在了（编辑态显示全部点）→ 再选中它 → 「改回未处理」。

**D. 数据**

```bash
sqlite3 ~/.local/share/com.example.map/map.db \
  "pragma user_version;                                        -- 期望 11
   select source, count(*) from points where deleted_at is null group by 1;
   --   期望 manual×686（老点没变）+ 你新记的点是 recorded
   select count(*) from points where processed = 1;             -- 你标记过的那些
   select count(*) from points where source='recorded' and processed=0;  -- 浏览态会显示的"
```

## 8. 爆炸半径与回滚

| 项 | 说明 |
|----|------|
| schema | v11 加一列（`NOT NULL DEFAULT 0`），老点自动"未处理"；`source` 加值不需要迁移 |
| 对现有地图 | **外观零变化**：真库 686 个点全是 `manual`（画图顶点），浏览态本来就不显示它们 |
| 唯一"行为变了"的地方 | **编辑态点变少了**（抽稀）与 **zoom < 15 不显示点** —— 这正是这一章要的 |
| 吸附 | **不受影响**：抽稀只过滤"画什么"，`hitNearestPoint` 仍然对**全部点**吸附（见 §9 R-22-1） |
| 回滚 | 代码回到上一版即可；多出来的 `processed` 列与 `recorded` 值旧代码会读成 `0`/`manual`（不报错） |

## 9. 遗留

| ID | 项 | 说明 |
|----|----|------|
| R-22-1 | **看得见的点和能吸附的点不完全一致** | 抽稀只影响显示：某个点可能没画出来但仍能被吸附（它在某个画出来的点旁边一两像素内，肉眼上没差别）。反过来做（"看不见就不能吸"）会在 zoom < 15 时让**连线彻底没法用**，所以没走那条路 |
| R-22-2 | 没有"显示全部点"的临时开关 | 抽稀规则是硬的。如果某个场景需要看全（例如排查脏点），现在得放大 |
| R-22-3 | 没有批量标记"已处理" | 只能一个个点。记录一条街之后想一次清空，需要一个"把这一带记录点全标为已处理"的动作 |
| R-22-4 | 点表单里不能改"处理状态" | 入口只在点面板上（表单里再加一个开关是重复的入口） |
| R-22-5 | 抽稀网格的**格内优先级**只有"有名字优先" | 没做"被线用到的优先"之类更复杂的排序 —— 那会让"哪几个点画出来"变得难以预料 |
| R-22-6 | 旧的 `test/` 继续失效 | 按 `AGENTS.md` §1 不修、不管、不跑 |
